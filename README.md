# Flutter Demo Application

Это демонстрационное приложение на Flutter, показывающее базовую начальную страницу.

## Функциональность

- Отображение начальной страницы с заголовком
- Отображение иконки и приветственного текста
- Адаптивный дизайн с использованием Material Design

## Структура проекта

```
lib/
├── main.dart          # Точка входа приложения
pubspec.yaml           # Файл зависимостей
README.md              # Этот файл
```

## Запуск приложения

Для запуска приложения выполните команду:

```bash
flutter run
```

## Зависимости

- flutter: sdk flutter

## bot-haibo: проекты и CapMonster

Ключевые запросы для основного сценария `yandex_search_visit.js` редактируются в `bot-haibo/projects.json`. Для проекта ремонта квартир используется блок `rem-kazan`, поле `queries`.

Запуск проектов:

- `bot-haibo/run-rem-kazan.sh` — проект `rem-kazan`
- `bot-haibo/run-top-design.sh` — проект `top-design-remont`
- `bot-haibo/remont-okon.sh` — проект `remont-okon`
- `bot-haibo/horgos-auto.sh` — проект `horgos-auto`

Первый запуск на новом компьютере:

```bash
cd bot-haibo
npm install
cp .env.example .env
cp config/captcha.example.json config/captcha.json
```

После этого заполните `.env` данными прокси, а в `config/captcha.json` укажите `cloud.api_key` CapMonster.

### Установка и обновление на сервере

Для Linux-сервера нужны Node.js версии не ниже 20 с npm (ограничение закреплённых зависимостей) и Python 3 с модулем `venv`. Команды ниже выполняются из корня репозитория:

```bash
git pull --ff-only origin main
cd bot-haibo
npm ci
python3 -m venv .venv
.venv/bin/python -m pip install requests
# Создать настройки только при их отсутствии:
test -f .env || cp .env.example .env
test -f config/captcha.json || cp config/captcha.example.json config/captcha.json
chmod 600 .env config/captcha.json
```

Один раз заполните на сервере `HAIBO_PROXY_HOST`, `HAIBO_PROXY_PORT`, `HAIBO_PROXY_USERNAME`, `HAIBO_PROXY_PASSWORD` в `.env` и `cloud.api_key` в `config/captcha.json`. Эти файлы содержат секреты, исключены из Git и сохраняются при последующих `git pull`. Ключи не передаются через GitHub. Профили браузера и зависимости также не входят в репозиторий.

На Ubuntu/Debian системные библиотеки Chrome можно установить командой `sudo npx puppeteer browsers install chrome --install-deps` из `bot-haibo` (потребуются права администратора). Затем под обычным пользователем установите браузер и запустите нужный проект:

```bash
npx puppeteer browsers install chrome
export HAIBO_PYTHON="$PWD/.venv/bin/python"
"$HAIBO_PYTHON" solve_captcha.py --self-test --output json
HAIBO_HEADLESS=1 node yandex_search_visit.js --project horgos-auto
```

Вместо `horgos-auto` можно указать любой ключ из `projects.json`. `HAIBO_HEADLESS=1` нужен для запуска без дисплея; сценарий поиска использует именно эту переменную, а не `HEADLESS`. Проверка `--self-test` не создаёт платную задачу. После обновления кода перезапустите процесс бота своим обычным способом; `git pull` сам его не перезапускает. При неизменных зависимостях повторно устанавливать Python-пакеты и Chrome не требуется. Запуск на конкретном сервере требует отдельной проверки.

### Профили по внешнему IP

Бот сохраняет отдельный Chromium-профиль для каждой комбинации проекта, режима устройства и внешнего IP:

```text
bot-haibo/.profiles/by-ip/<project>/<mobile-or-desktop>/ip-<hash>/
```

Новый IP получает пустой профиль и проходит прогрев перед поиском. Если все посещения прогрева не удались, поиск не начинается: бот ждёт и повторяет запуск сессии. При возвращении знакомого IP используются его сохранённые cookies, localStorage и история. Данные между профилями не копируются. Старые `.profiles/<project>` остаются на месте и автоматически не используются новой схемой.

Для проверки IP применяется отдельный служебный профиль в `.profiles/.proxy-check/`. IP проверяется также после открытия выбранного профиля, после прогрева и между запросами. Если адрес меняется, выбирается соответствующий профиль. Прокси может сменить IP внутри запроса; гарантировать постоянство адреса во время загрузки может только поставщик прокси. В сводке выводится проверенный перед запросом IP и `profile=ip-...`.

Прогрев включён по умолчанию (`HAIBO_WARM_SESSION=1`, `HAIBO_WARM_SITES=4`). Отключать его можно для уже прогретых профилей; новый профиль при отключённом прогреве не начнёт поиск. Само наличие истории не гарантирует, что поисковик сочтёт сессию посещением человека. Профили накапливаются на диске; удаление конкретной папки удаляет её историю. Не удаляйте профиль работающего Chromium.

Каждый сайт прогрева имеет общий лимит 60 секунд (`HAIBO_WARM_SITE_MAX_MS`, от 1000 до 300000 мс). Открытие сайта выполняется один раз с ожиданием до 20 секунд. Лимит охватывает создание вкладки, настройку, прокрутку, действия и возврат назад. Закрытие вкладки ограничено отдельно: если обычное закрытие не отвечает, бот пытается закрыть вкладку через CDP и перейти к следующему сайту. Если Chromium не позволяет закрыть вкладку, завершается только его собственный процесс, после чего сессия запускается повторно с обычной паузой. Строка `opening ... (budget ...s)` и этап ошибки показывают, где находится прогрев.

### Страницы поисковой выдачи

Бот проверяет до семи страниц выдачи: вторая запрашивается с `p=1`, седьмая с `p=6`. Перед поиском целевой ссылки проверяются номер страницы, текст запроса и наличие изменившихся результатов. После CAPTCHA бот один раз восстанавливает нужный адрес, если оказался на другой странице. Если переход не подтверждён, пагинация прекращается; лог показывает причину и число действительно проверенных страниц. Существующий прямой переход на сайт остаётся отдельным результатом `DIRECT`.

### Просмотр внутренних страниц

Бот прокручивает содержимое и пытается открыть 2–4 другие страницы через видимые ссылки. Перекрытая или неподвижная после клика ссылка не засчитывается как переход. В логах выводятся `Confirmed internal page` и итог `Confirmed internal pages`, отдельно для кликов и прямого открытия обнаруженных URL. На странице с внутренним прокручиваемым контейнером учитывается его позиция, а не только `window.scrollY`.

Для `imperator-kzn.ru` предусмотрены его реальные окна: мобильное уведомление о cookies подтверждается кнопкой «Хорошо», затем режим просмотра меню выбирается кнопкой «Самовывоз». Адрес не вводится, товары не добавляются, заказ не оформляется. Неизвестные окна не закрываются автоматически. Эти действия нужны для доступа к страницам сайта и не гарантируют классификацию автоматического посещения как человеческого.

Резервная точка исходников перед этой схемой: коммит `4e8550f` в `origin/main`. Для возврата только изменённого существующего кода из корня проекта:

```bash
git restore --source=4e8550f -- bot-haibo/yandex_search_visit.js bot-haibo/visit-result.js README.md PROJECT_CONTEXT.md
```

Команда отменяет текущие правки указанных файлов. Старые профили и секретные локальные настройки в резервный Git-коммит не включены и остаются на диске.

Текущая схема CapMonster:

- `solve_captcha.py --self-test` проверяет запуск Python, импорт `requests` и runtime-конфиг без создания платной задачи.
- `yandex_search_visit.js` запускает preflight перед solver-попытками.
- После навигации и перед запуском/повтором решателя бот перепроверяет страницу: если уже открыта выдача без CAPTCHA, продолжает поиск без решателя. Если состояние страницы определить не удалось, новая задача не создаётся.
- CapMonster API transport идёт напрямую с Mac: `route_api_via_proxy: false`.
- Мобильный прокси передаётся только в payload задачи CapMonster как task proxy.
- После transient transport error solver продолжает polling того же `taskId`.
- Если CapMonster остаётся в `processing` до wall-clock timeout, JS останавливает дальнейшие solver retries, чтобы не создавать новые платные задачи.
