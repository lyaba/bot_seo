# Flutter Demo Application

Это демонстрационное приложение на Flutter, показывающее базовую начальную страницу.

## Функциональность

- Отображение начальной страницы с заголовком
- Отображение иконки и приветственного текста
- Адаптивный дизайн с использованием Material Design

## Структура проекта

```
lib/
├── main.dart          # Точка входа приложения
pubspec.yaml           # Файл зависимостей
README.md              # Этот файл
```

## Запуск приложения

Для запуска приложения выполните команду:

```bash
flutter run
```

- flutter: sdk flutter

## bot-haibo: проекты и CapMonster

Ключевые запросы для основного сценария `yandex_search_visit.js` редактируются в `bot-haibo/projects.json`. Для проекта ремонта квартир используется блок `rem-kazan`, поле `queries`.

Запуск проектов:

- `bot-haibo/run-rem-kazan.sh` — проект `rem-kazan`
- `bot-haibo/run-top-design.sh` — проект `top-design-remont`
- `bot-haibo/remont-okon.sh` — проект `remont-okon`
- `bot-haibo/horgos-auto.sh` — проект `horgos-auto`

Первый запуск на новом компьютере:

```bash
cd bot-haibo
npm install
cp .env.example .env
cp config/captcha.example.json config/captcha.json
```

После этого заполните `.env` данными прокси, а в `config/captcha.json` укажите `cloud.api_key` CapMonster.

### Профили по внешнему IP

Бот сохраняет отдельный Chromium-профиль для каждой комбинации проекта, режима устройства и внешнего IP:

```text
bot-haibo/.profiles/by-ip/<project>/<mobile-or-desktop>/ip-<hash>/
```

Новый IP получает пустой профиль и проходит прогрев перед поиском. Если все посещения прогрева не удались, поиск не начинается: бот ждёт и повторяет запуск сессии. При возвращении знакомого IP используются его сохранённые cookies, localStorage и история. Данные между профилями не копируются. Старые `.profiles/<project>` остаются на месте и автоматически не используются новой схемой.

Для проверки IP применяется отдельный служебный профиль в `.profiles/.proxy-check/`. IP проверяется также после открытия выбранного профиля, после прогрева и между запросами. Если адрес меняется, выбирается соответствующий профиль. Прокси может сменить IP внутри запроса; гарантировать постоянство адреса во время загрузки может только поставщик прокси. В сводке выводится проверенный перед запросом IP и `profile=ip-...`.

Прогрев включён по умолчанию (`HAIBO_WARM_SESSION=1`, `HAIBO_WARM_SITES=4`). Отключать его можно для уже прогретых профилей; новый профиль при отключённом прогреве не начнёт поиск. Само наличие истории не гарантирует, что поисковик сочтёт сессию посещением человека. Профили накапливаются на диске; удаление конкретной папки удаляет её историю. Не удаляйте профиль работающего Chromium.

Резервная точка исходников перед этой схемой: коммит `4e8550f` в `origin/main`. Для возврата только изменённого существующего кода из корня проекта:

```bash
git restore --source=4e8550f -- bot-haibo/yandex_search_visit.js bot-haibo/visit-result.js README.md PROJECT_CONTEXT.md
```

Команда отменяет текущие правки указанных файлов. Старые профили и секретные локальные настройки в резервный Git-коммит не включены и остаются на диске.

Текущая схема CapMonster:

- `solve_captcha.py --self-test` проверяет запуск Python, импорт `requests` и runtime-конфиг без создания платной задачи.
- `yandex_search_visit.js` запускает preflight перед solver-попытками.
- CapMonster API transport идёт напрямую с Mac: `route_api_via_proxy: false`.
- Мобильный прокси передаётся только в payload задачи CapMonster как task proxy.
- После transient transport error solver продолжает polling того же `taskId`.
- Если CapMonster остаётся в `processing` до wall-clock timeout, JS останавливает дальнейшие solver retries, чтобы не создавать новые платные задачи.
